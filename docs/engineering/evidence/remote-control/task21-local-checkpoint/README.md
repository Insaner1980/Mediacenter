## Interoperability and deterministic harness

The Rust test parses all 88 shared method fixtures into actual typed server DTOs and serializes actual Rust wire strings; Kotlin consumes those strings, not independently copied Kotlin fixtures. Request and reply method sets are checked against all 88 Kotlin `MethodName` entries, with structural request/reply roundtrip equality. There are 101 typed replies including pairing outcomes/QR, stale replacement preview, accepted preparation, selection bounds and all six operation outcomes. Two snapshots, hello, decimal strings above 2^53 and at u64 max, 44 malformed/semantic/oversize requests and two stale-preview failures are non-vacuous fixed counts. Kotlin explicitly rejects a numeric snapshot counter and overflowing decimal hello counter derived from the real exported bytes. These checks fail on missing required serializer fields, wrong method-result associations, parser coercion/precision drift, loss of optional fixture fields, or relaxed bounded-input behavior. They are not formal draft2020 JSON Schema validation.

The Dispatcher conversation uses a temporary real AppState/SQLite journal and an existing fake pause effect. It records actual accepted, terminal lookup, repeated original request and conflicting request bytes using the same `RemoteReply<Value>` serializer used after server dispatch. Native effect count and journal row count are each asserted equal to one in Rust; Kotlin parses the generated request/replies, checks the same operation ID, succeeded terminal status, duplicate acceptance and failure variant. UUID/epoch values are retained exactly. Outcomes are deterministic; fresh runs can have different real opaque IDs. This is a real dispatcher/codec recovery test with fake native playback, not proof that mpv played or HDMI sound was heard.

The exported player event arrives before the initial snapshot. Real `RemoteStateReducer.apply` buffers it, applies the snapshot, advances the >2^53 sequence to the paused state, rejects an event gap and clears readiness, then accepts a fresh snapshot. This exercises the actual client startup/race seam.
